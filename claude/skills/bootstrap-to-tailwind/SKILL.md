# Bootstrap to Tailwind Form Migration

## Step 0: Discovery — Tracing the Form End-to-End (DO THIS FIRST)

Before converting anything, you MUST trace the full chain from URL to rendered form. Skipping this leads to mismatched `data-toggle` values, wrong base templates, broken buttons, and failing tests.

### 1. Find the URL pattern and view

Start from the URL (e.g. `/cal/services/53/`). Search `**/urls*.py` files:
- The main app routes via `TutorCruncher/urls.py` → e.g. `path('cal/', include('TutorCruncher.schedule.urls.auth', namespace='cal'))`
- Sub-URLs are in files like `TutorCruncher/schedule/urls/_services.py`
- Service detail pages use a dispatcher function in `base.py` that routes by role (admin/contractor/client)

### 2. Find the card that triggers the form

Detail pages render cards via `CardRenderer` subclasses in `display_cards.py` files. Look for:
- **Header buttons**: defined in `_get_header_buttons()` on the card class — these are the "Add" buttons
- **Per-item action buttons**: defined in the `item_renderer` Jinja template (e.g. `card_renderer.jinja`) — these are Edit/Remove dropdowns per item

The `Button` dataclass (`TutorCruncher/common/templating/components/buttons.py`) generates `data-toggle` attributes:
- `open_in_modal=True` → `data-toggle="crud-modal"`
- `open_in_sidepanel=True` → `data-toggle="side-panel"`

### 3. Find the CRUD class / form view

The button URL (e.g. `service-RCRs-add`) is auto-generated by `GenericCRUD.get_urls(prefix)` in `TutorCruncher/common/crud.py`:
```python
path(url_prefix + 'add/', cls.create_view(), name='%s-add' % prefix)
path(url_prefix + 'edit/<int:pk>/', cls.update_view(), name='%s-edit' % prefix)
path(url_prefix + 'delete/<int:pk>/', cls.delete_view(), name='%s-delete' % prefix)
```

The CRUD class defines:
- `get_form()` — builds the dynamic `TmpForm`
- `modal_template_name` — the Jinja template for AJAX rendering
- `form_base_class` — `GenericEditForm` (Bootstrap) or `GenericEditTailwindForm` (Tailwind)

### 4. Find the template and check what it extends

The CRUD's `modal_template_name` points to a Jinja template. Check what it extends:
- `common/form_modal.jinja` → modal (extends `base-modal.jinja`, contains `<!--IS_MODAL-->`)
- `common/form_side_panel.jinja` → side panel (extends `base-side-panel.jinja`, contains `<!--IS_SIDE_PANEL-->`)

If `modal_template_name` is not set, `ModalMixin` defaults to `common/form_modal.jinja` for AJAX requests.

**IMPORTANT**: `form_modal.jinja` checks `form.is_tailwind_form` and uses `render_form()` for Tailwind forms. `form_side_panel.jinja` also supports this. Both fall back to `{{ form|bootstrap }}` for non-Tailwind forms.

### 5. Find the JS file

JS files are loaded two ways:
- **Via template**: `{{ js_data(js_file='recipient_charge_rate', ...) }}` in a `{% block modal_after_form %}` block
- **Via widget attr**: `self.fields['some_field'].widget.attrs['data-js'] = 'contractor_job'` in the form's `__init__`

Both end up as `data-js="filename"` in the HTML. `main.js:108` scans for `[data-js]` elements and dynamically imports `static/js2/defer/{filename}.js`.

Check the JS file for:
- Label hiding hacks (e.g. `$('label[for=id_recipient]').hide()`) — remove these after migration since Tailwind forms render proper labels
- Field show/hide logic (e.g. toggling pay rate field based on checkbox) — keep this
- Any `$('.form-group')` selectors — these target Bootstrap markup and may need updating to `.tw-input-wrapper` after migration

### tw-input-wrapper: Template vs JS Usage

`render_field()` already adds `tw-input-wrapper` to its own wrapping div (`<div class="tw:col-span-X tw-input-wrapper">`). This has two implications:

**Templates: Do NOT add `tw-input-wrapper` around `render_field()` calls.** It's redundant — double-wrapping.
```jinja
{# WRONG — double tw-input-wrapper #}
<div class="tw-input-wrapper">{{ render_field(form.name) }}</div>

{# CORRECT — render_field adds it internally #}
{{ render_field(form.name) }}

{# CORRECT — outer div for grid layout, no tw-input-wrapper needed #}
<div class="tw:col-span-6">{{ render_field(form.name) }}</div>
```

Only add `tw-input-wrapper` manually when wrapping **raw** field output (`{{ field }}`, `{{ form.field|safe }}`, raw `<input>` elements) — NOT when using `render_field()`.

**JS: `.closest('.tw-input-wrapper')` is correct.** JS uses this selector to find the field wrapper that `render_field` creates. When hiding fields rendered via `render_form()`, use `.closest('.tw-input-wrapper').parent().hide()` — the `.parent()` is needed to also hide the grid row wrapper (`tw:grid tw:md:grid-cols-12 tw:gap-4 tw:mb-4`) which would otherwise leave empty whitespace.

### 6. Check per-item action buttons in the item_renderer template

The `item_renderer` template (e.g. `schedule/conjobs/card_renderer.jinja`) renders each item in the card. Check:
- `dropdown()` macros with `data_attrs` — ensure `data-toggle` values match:
  - `{ 'toggle': 'crud-modal' }` for modal forms
  - `{ 'toggle': 'side-panel' }` for side panel forms
- `{ 'confirm': '...' }` for delete confirmations — these don't need template changes

### 7. Find and update tests

Search for tests that reference the form's URL name (e.g. `service-RCRs-add`). Common assertions to update:
- `assertContains(r, '<!--IS_SIDE_PANEL-->')` vs `assertContains(r, '<!--IS_MODAL-->')`
- `assert 'data-toggle="modal"' in ...` → `assert 'data-toggle="crud-modal"' in ...` or `assert 'data-toggle="side-panel"' in ...`
- Check test makes AJAX request with `HTTP_X_REQUESTED_WITH='XMLHttpRequest'` to trigger modal/side panel rendering

## Project Context

TutorCruncher is a Django application undergoing a UI redesign. We're migrating forms from Bootstrap-based rendering to Tailwind-based rendering.

## The Two Form Systems

**Bootstrap Forms (old):**
- Base classes: `TCBSForm`, `TCBSModelForm`
- Import: `from TutorCruncher.bootstrapform_jinja_plus.forms import BSForm`
- Layout defined as list of dicts with `'type': BSForm.TITLED`
- Rendered with `{{ form|bootstrap }}` in templates

**Tailwind Forms (new):**
- Base classes: `TCTailwindForm`, `TCTailwindModelForm`
- Import: `from TutorCruncher.common.forms import layout`
- Layout defined using dataclasses: `layout.L()`, `layout.S()`, `layout.F()`
- Have `is_tailwind_form = True` attribute
- Rendered with `{{ render_form(form) }}` in templates

## The Layout System

### layout.L (Layout)
The top-level container that holds sections:
```python
layout.L(sections=[...])
```

### layout.S (Section)
A section with rows of fields and optional styling:
```python
layout.S(
    title='Section Title',  # optional — controls default style (see SectionStyle below)
    style=layout.SectionStyle.divider,  # optional — explicit style override
    description='Optional description text',  # optional
    rows=[...]
)
```

### SectionStyle
Controls how a section is visually rendered. Three options:

- **`SectionStyle.card`** — Wraps content in a `basic_card` component with a bordered card header. **Default when `title` is provided.** Use for full-page forms with multiple sections.
- **`SectionStyle.divider`** — Renders a small heading + horizontal rule, then content. No card border. Use for side-panel forms (e.g. filters) to separate sections without heavy card borders.
- **`SectionStyle.plain`** — No wrapper, no title, just the fields. **Default when `title` is omitted.** Use for modals and single-section forms.

The default logic is:
```python
self.style = SectionStyle.card if self.title else SectionStyle.plain
```

**Kwarg ordering convention**: when specifying `style` explicitly, put it before `rows`:
```python
layout.S(title='Details', style=layout.SectionStyle.divider, rows=[...])
```

### Choosing the Right Style

| Context | Style | How |
|---------|-------|-----|
| **Modal forms** | `plain` | Omit `title` — the modal header already provides context. A card-inside-a-modal creates ugly nesting. |
| **Full-page forms with multiple sections** | `card` (default) | Just provide a `title` — the default card style wraps each section in a bordered card. |
| **Side-panel forms (e.g. filters)** | `divider` | Set `style=layout.SectionStyle.divider` — gives visual separation without heavy card borders inside the panel. |
| **Single-section forms** | `plain` | Omit `title` — no need for extra chrome around one section. |

### layout.F (Field)
For advanced field configuration (optional - usually just use tuples):
```python
layout.F(name='field_name', width=6, textarea_rows=3)
```

## Row and Field Syntax

Rows are lists of fields. Fields can be:
- **String: `'field_name'`** - uses default width of **12** (full width) - **PREFERRED for full-width fields**
- **Tuple: `('field_name', width)`** - explicit width, use when NOT full-width
- **layout.F object** - for advanced config (textarea rows, etc.)

Width is based on 12-column grid:
- `12` = full width (default when using string format)
- `6` = half width (2 fields per row)
- `4` = third width (3 fields per row)
- `3` = quarter width (4 fields per row)

### Examples

**Single field per row (full width) - use string format:**
```python
# PREFERRED - clean and simple
rows=[['status']]

# Also works but verbose
rows=[[('status', 12)]]
```

**Two fields per row (half width each) - must use tuples:**
```python
rows=[[('date_from', 6), ('date_to', 6)]]
```

**Multiple rows - mix string and tuple as appropriate:**
```python
rows=[
    ['field1'],  # full width - use string
    [('field2', 6), ('field3', 6)],  # half width each - use tuples
    [('field4', 4), ('field5', 4), ('field6', 4)],  # third width - use tuples
]
```

## Conversion Pattern

### Before (Bootstrap):
```python
from TutorCruncher.bootstrapform_jinja_plus.forms import BSForm
from TutorCruncher.common.forms.bootstrap import TCBSForm

class SomeForm(TCBSForm):
    # ... field definitions ...

    def get_layout(self):
        return [
            {'title': 'Date Range', 'type': BSForm.TITLED, 'rows': [['date__from', 'date__to']]},
            {'title': 'Options', 'type': BSForm.TITLED, 'rows': [['status'], ['category']]},
        ]
```

### After (Tailwind):
```python
from TutorCruncher.common.forms import layout
from TutorCruncher.common.forms.tailwind import TCTailwindForm

class SomeForm(TCTailwindForm):
    # ... field definitions ...

    def get_layout(self) -> layout.L:  # Always add type hint
        return layout.L(sections=[
            layout.S(title='Date Range', rows=[[('date__from', 6), ('date__to', 6)]]),
            layout.S(title='Options', rows=[['status'], ['category']]),  # Full-width fields use string format
        ])
```

## Conversion Checklist

1. **Update base class:**
   - `TCBSForm` → `TCTailwindForm`
   - `TCBSModelForm` → `TCTailwindModelForm`

2. **Update imports:**
   - Add `from TutorCruncher.common.forms import layout`
   - Add `from TutorCruncher.common.forms.tailwind import TCTailwindForm` (or TCTailwindModelForm)
   - Remove `from TutorCruncher.bootstrapform_jinja_plus.forms import BSForm` if no longer used
   - Remove `from TutorCruncher.common.forms.bootstrap import TCBSForm` if no longer used

3. **Define `get_layout()` (CRITICAL - DO NOT SKIP):**
   - **Every Tailwind form MUST have a `get_layout()` method.** Without it, `render_form(form)` has no sections and renders nothing.
   - Add return type hint: `def get_layout(self) -> layout.L:`
   - Wrap return value in `layout.L(sections=[...])`
   - Convert each dict to `layout.S(title='...', rows=[...])`
   - For full-width fields, use string format: `['field']` (default width is 12)
   - For fields sharing a row, use tuples with explicit widths: `[('f1', 6), ('f2', 6)]`
   - **Include ALL fields** in the layout, even conditionally visible ones - the layout system automatically skips fields that have been popped from `self.fields`

4. **Move template conditionals into the form (CRITICAL):**
   - The old Bootstrap templates often had conditional rendering: `{% if use_agents %}`, `{% if form.currency %}`, `{% if form.invoice_now %}`, etc.
   - **Do NOT keep these conditionals in the template.** Move them into the form using one of two approaches:

   **Approach A: Pop fields** — when the feature is completely disabled and the form should NOT process submitted data for those fields:
   ```python
   # use_agents is a hard toggle — if disabled, agent data should never be processed
   if not branch.use_agents:
       self.fields.pop('agent', None)
       self.fields.pop('agent_percentage', None)
   ```

   **Approach B: Conditional layout** — when the fields should be hidden from the UI but the form must still accept/process POST data:
   ```python
   # Store the condition for use in get_layout()
   self._use_foreign_exchange = branch.use_foreign_exchange

   def get_layout(self) -> layout.L:
       rows = [['category'], ['description'], ['date_occurred']]
       if self._use_foreign_exchange:
           rows += [['use_alt_currency'], ['currency']]
       rows += [['client'], ['contractor']]
       return layout.L(sections=[layout.S(title='Form', rows=rows)])
   ```

   **How to decide:** Check the existing tests. If tests POST data for those fields without enabling the feature flag, the original form was processing that data — use conditional layout (Approach B). If tests always enable the feature flag first, the form rejects data when disabled — use field popping (Approach A).

5. **Update the template:**
   - Replace all `{{ form.field|bootstrap }}` with `{{ render_form(form) }}`
   - Add `{% from 'forms/form.jinja' import render_form %}` import
   - Remove all conditional field rendering (`{% if use_agents %}`, etc.) - this is now in the form
   - Remove duplicate `non_field_errors` blocks - `render_form` already handles them
   - Follow the `filter.jinja` pattern: the template should just call `render_form(form)` and nothing else for fields
   - Reference template: `TutorCruncher/common/templates/common/filter.jinja`
   - **Dedicated templates** (only used by one form): use `render_form(form)` directly — no `is_tailwind_form` check needed
   - **Shared templates** (used by multiple forms, some not yet converted): use the `is_tailwind_form` guard:
     ```jinja
     {% if form.is_tailwind_form %}
       {{ render_form(form) }}
     {% else %}
       {{ form|bootstrap }}
     {% endif %}
     ```

6. **Update the view button for the form's container:**
   - **Side panel forms**: If the template extends `base-side-panel.jinja`, the button must have `open_in_sidepanel=True`:
     ```python
     Button(url=url, text='Add', icon='fas fa-plus', small=True, open_in_sidepanel=True)
     ```
   - **Modal forms**: If the template extends `base-modal.jinja` (or `form_modal.jinja`), the button must have `open_in_modal=True`:
     ```python
     Button(url=url, text='Add to Job', icon='fas fa-plus', small=True, open_in_modal=True)
     ```
   - Check the view's `display_cards.py` or similar file that generates the button
   - Look at sibling cards for the pattern — e.g. `ClientDetailsServicesCard` already had `open_in_modal=True`, so `ConDetailsServicesCard` needed it too
   - Without these flags, the form renders as a broken full page instead of in its container

7. **Verify:**
   - `get_layout()` has `-> layout.L` type hint
   - Modal forms use `layout.S(rows=[...])` with **no title** (plain style) — the modal provides the title
   - Full-page multi-section forms use `card` style (default when title is provided) — no explicit `style=` needed
   - Side-panel forms use `style=layout.SectionStyle.divider` for visual separation without card borders
   - Imports are correct
   - Template has NO `|bootstrap` calls
   - Template has NO conditional field rendering (moved to form `__init__`)

8. **Post-conversion validation (MANDATORY):**
   After writing the converted code, grep the changed files for redundant explicit width 12:
   ```bash
   grep -n "('.*', 12)" TutorCruncher/path/to/converted_file.py
   ```
   Any match where the field is the **only field in its row** must be replaced with string format:
   - `[('field_name', 12)]` → `['field_name']`
   - `[('field_name', 12), ('other', 6)]` → leave as-is (multiple fields in row)

   **Do not skip this step.** It catches the most common conversion mistake.

## WRONG: Rendering Fields Individually (for regular forms)

**For regular forms, NEVER render fields one by one with `render_field()` in the template.** This is the wrong approach:
```jinja
{# WRONG for regular forms - do not do this #}
{{ render_field(form.category) }}
{{ render_field(form.description) }}
{{ render_field(form.date_occurred) }}
```

This leads to:
- Creating unnecessary custom widgets (Textarea, NumberInput, etc.)
- Template still managing field layout and conditionals
- Inconsistent rendering compared to other Tailwind forms

**CORRECT for regular forms: Define `get_layout()` on the form and call `render_form(form)` once in the template.**

**EXCEPTION: Formsets** — formsets MUST use `render_field()` individually because `render_form()` / `get_layout()` doesn't apply. See [Converting Formsets](#converting-formsets-template-only) below.

**EXCEPTION: Composite template macros** — some fields need a custom rendering structure that `render_form()` / `render_field()` cannot express: a card wrapper, a custom header with extra controls (e.g., "Select All" checkbox), or a body/footer layout. These fields should be **excluded from `get_layout()`** and rendered manually in the template using a dedicated macro.

Example: `select_multiple_panel` in `macro/display_functions.jinja` renders a `ModelMultipleChoiceField` as a card with a header (label + right-aligned "Select All" checkbox), a body (checkbox list), and help text below. This structure doesn't fit `render_field()`'s flat `label → widget → errors → help_text` flow.

**How to handle:**
1. **Don't put the field in `get_layout()`** — `render_form()` will skip it
2. **Update the existing Bootstrap macro to Tailwind** — replace Bootstrap classes with Tailwind equivalents, keep the same structure
3. **Render manually in the template** after `{{ render_form(form) }}`
4. **If ordering matters**, use JS to reposition the block (same pattern as `$('#details').after($availability)` in `appointment_form.js`)
5. **Remove any JS that was injecting elements** to compensate for what `render_field()` couldn't do — the macro handles it now

**How to recognize these fields:** Look for fields that the original Bootstrap template rendered via a custom macro (e.g., `select_multiple_panel`) instead of `{{ form.field|bootstrap }}`. If it had its own macro, it probably needs one in Tailwind too.

**EXCEPTION: Template-controlled layout** — when the template renders ALL form fields manually via `render_field()` because the layout requires custom HTML structure that `render_form()` can't express (e.g., a field and submit button side-by-side in a flex container). In this case, `get_layout()` is dead code — `render_form()` is never called, so the layout is never used.

**How to handle:**
1. **Do NOT define `get_layout()`** on the form — it will never be called
2. The form only needs the Tailwind base class (`TCTailwindForm` / `TCTailwindModelForm`) for widget upgrades
3. Fields are rendered individually in the template with `render_field(form.field_name)`

**How to recognize:** Check the template. If it uses `render_field()` for every field and never calls `render_form(form)`, the form doesn't need `get_layout()`.

Example: `ApproveReportsForm` — the template renders `send_emails` via `render_field()` inside a flex container alongside a submit button:
```jinja
<div class="tw:mt-4 tw:flex tw:items-start tw:justify-between tw:gap-4 ...">
  {{ render_field(form.send_emails) }}
  {{ button(type='submit', variant='primary', text=submit_label or 'Submit', icon='fas fa-check') }}
</div>
```

## Converting GenericCRUD Forms (Dynamic Forms)

`GenericCRUD` (`TutorCruncher/common/crud.py`) dynamically creates form classes at runtime via metaclass magic in `get_form()`. These forms don't exist as regular Python classes — they're built on the fly. This requires a different conversion approach than regular forms.

### Why It's Different

Regular forms: you edit the class, change the base, add `get_layout()`. Done.

GenericCRUD forms: there's no form class to edit. The form is created dynamically inside `get_form()`, inheriting from `GenericEditForm` (which extends `TCBSModelForm`). You can't change `GenericEditForm` without affecting **all** CRUD classes.

### The Solution: Opt-In Hooks

`GenericCRUD` has two hooks that let individual CRUD subclasses opt into Tailwind:

1. **`form_base_class`** — class attribute, defaults to `GenericEditForm` (Bootstrap). Override to `GenericEditTailwindForm` to switch to Tailwind.
2. **`get_form_layout()`** — classmethod, returns `None` by default. Override to return a `layout.L()` object.

The dynamic `TmpForm` created in `get_form()` uses `cls.form_base_class` as its base and delegates `get_layout()` to `cls.get_form_layout()`.

### `GenericEditTailwindForm`

Defined in `TutorCruncher/common/crud.py`. It's the Tailwind equivalent of `GenericEditForm` — extends `TCTailwindModelForm` and duplicates the queryset filtering logic (filtering `ModelChoiceField` querysets, setting empty labels, building choices).

This duplication exists because `GenericEditForm` (Bootstrap) can't be changed without affecting all CRUDs. Once all GenericCRUD subclasses are migrated, the Bootstrap version can be removed.

### Conversion Steps for a GenericCRUD Subclass

1. **Import** `GenericEditTailwindForm` and `layout`:
   ```python
   from TutorCruncher.common.crud import GenericCRUD, GenericEditTailwindForm
   from TutorCruncher.common.forms import layout
   ```

2. **Set `form_base_class`** on the CRUD class:
   ```python
   class MyCRUD(GenericCRUD):
       form_base_class = GenericEditTailwindForm
   ```

3. **Add `get_form_layout()`** with the field layout:
   ```python
   @classmethod
   def get_form_layout(cls) -> layout.L:
       return layout.L(sections=[
           layout.S(title='Details', rows=[
               ['name'],
               ['description'],
               [('field_a', 6), ('field_b', 6)],
           ]),
       ])
   ```

4. **Update the template** — same as regular forms: `{{ form|bootstrap }}` → `{{ render_form(form) }}`

5. **No blast radius** — other CRUD classes inherit `form_base_class = GenericEditForm` by default, so they're unaffected.

### Example: TaskCRUD Conversion

```python
class TaskCRUD(ModalMixin, GenericCRUD):
    model = Task
    fields = ['name', 'description', 'task_type', 'due_dt', 'admin', 'role', 'service', 'repeater', 'repeat_every']
    form_base_class = GenericEditTailwindForm  # opt into Tailwind

    def get_form_layout(cls) -> layout.L:
        return layout.L(sections=[
            layout.S(title='Task Details', rows=[
                ['name'],
                ['description'],
                ['task_type'],
                ['due_dt'],
                ['admin'],
                ['role'],
                ['service'],
                [('repeater', 6), ('repeat_every', 6)],
            ]),
        ])
```

### Key Insight: Layout Lives on the CRUD, Not the Form

For regular forms, `get_layout()` is a method on the form class. For GenericCRUD forms, the layout is defined on the **CRUD class** via `get_form_layout()`, then injected into the dynamic form. This is because you don't have a form class to put it on.

### GenericCRUD Architecture — How the Pieces Fit Together

There is **no form class written anywhere** for GenericCRUD models. Everything is manufactured at runtime by factory methods on the CRUD class. Understanding this flow is essential before making changes.

#### The Form Factory — `get_form()`

`GenericCRUD.get_form()` dynamically creates a `TmpForm` class:

```
get_form() creates TmpForm(cls.form_base_class):

  Base class decided by:
    cls.form_base_class ──► GenericEditForm (Bootstrap)
                         OR GenericEditTailwindForm (Tailwind)

  Meta is built from CRUD class attrs:
    model  = cls.model
    fields = cls.fields

  Every method delegates back to the CRUD class:
    __init__()           → cls.form_pre_init_handler() + cls.form_init_handler()
    clean()              → cls.form_clean_handler()
    save()               → cls.save_obj_handler() + cls.edit_action()
    get_layout()         → cls.get_form_layout()
    get_form_qs_kwargs() → cls.get_form_qs_kwargs()
    get_field_qs()       → cls.get_field_qs()
```

#### The View Factory — `create_view()` / `update_view()`

These factory methods create `TmpCreateView` / `TmpUpdateView` classes:

```
create_view() creates TmpCreateView(PermissionMixin, ModalMixin, BasicPage, CreateView):

  form_class          = cls.get_form()          ← the TmpForm above
  template_name       = cls.edit_template        ← default: 'common/edit_basic.jinja'
  modal_template_name = cls.modal_template_name  ← default: None

  ModalMixin.dispatch() decides which template to use:
    if AJAX request → modal_template_name (or default 'common/form_modal.jinja')
    if full page    → edit_template ('common/edit_basic.jinja')
```

#### The Base Form Classes

```
                    GenericEditFormMixin
                    (queryset filtering, checkbox widgets,
                     empty labels — shared by both paths)
                      /                    \
    GenericEditForm                    GenericEditTailwindForm
    (+ TCBSModelForm)                 (+ TCTailwindModelForm)
         │                                     │
     Bootstrap path                        Tailwind path
     {{ form|bootstrap }}                  {{ render_form(form) }}
     get_layout() → list of dicts          get_layout() → layout.L()
```

`GenericEditFormMixin` handles queryset filtering for `ModelChoiceField`s (branch/agency scoping, per-field querysets, empty labels). Both `GenericEditForm` and `GenericEditTailwindForm` inherit this identically — the only difference is the form rendering base class.

#### GenericCRUDL Adds List View + Buttons

`GenericCRUDL(GenericCRUD)` adds:
- `list_view()` — factory for `TmpListView` with table display
- `get_list_buttons()` — "Add" button with `open_in_modal=True` (default)
- `detail_modal_view` / `detail_sidepanel_view` — controls `data-toggle` on list item links
- `get_urls()` adds `list/` URL in addition to `add/`, `edit/<pk>/`, `delete/<pk>/`

#### Request Flow (Example: ReminderCRUDL with Bootstrap)

```
User clicks "Add Reminder" button (open_in_modal=True → data-toggle="crud-modal")
  │
  ▼ JS intercepts, makes AJAX GET
  │
TmpCreateView.dispatch()
  │ request.is_ajax = True
  │ modal_template_name = None → defaults to 'common/form_modal.jinja'
  │
  ▼
TmpForm(GenericEditForm) → form.is_tailwind_form = False
  │
  ▼
form_modal.jinja:
  {% if form.is_tailwind_form %}  ← False
    {{ render_form(form) }}
  {% else %}
    {{ form|bootstrap }}          ← THIS PATH
  {% endif %}
```

### Moving a GenericCRUDL Form from Modal to Side Panel

When converting a GenericCRUDL form AND changing its container from modal to side panel, there are changes beyond the standard Tailwind conversion.

#### Choosing a Template: Shared vs Custom

**Use the shared `form_side_panel.jinja`** when:
- The form has no JS
- No extra context needs rendering outside the form (no service links, no delete button in footer)
- The standard side panel layout (header, scrollable form body, cancel+save footer) is sufficient

**Create a custom side panel template** when (like TaskCRUD or AHC):
- The form has associated JS that needs `{{ js_data(...) }}` calls
- The footer needs extra buttons (e.g., delete)
- The header needs extra actions (e.g., button menu)
- Extra context is rendered outside the form (e.g., service/appointment links)

Note: custom side panel templates may or may not extend `base-side-panel.jinja`. TaskCRUD's template is a raw HTML fragment (no `{% extends %}`), while AHC's extends `base-side-panel.jinja`. Both work — the side panel JS handles injection either way.

#### Changes Required on the CRUD Class

```python
class MyCRUDL(BranchCRUDL):
    # 1. Opt into Tailwind (standard conversion)
    form_base_class = GenericEditTailwindForm

    # 2. Point to side panel template for AJAX requests
    modal_template_name = 'common/form_side_panel.jinja'

    # 3. Make list item edit links open in side panel
    detail_sidepanel_view = True

    # 4. Override the "Add" button to use side panel instead of modal
    @classmethod
    def get_list_buttons(cls, request):
        return [
            Button(
                text='Add ' + str(cls.model._meta.verbose_name),
                url=cls._relative_url(request, 'add'),
                icon='fas fa-plus',
                variant=ButtonVariant.primary,
                open_in_sidepanel=True,  # was open_in_modal=True in GenericCRUDL
            )
        ]

    # 5. Add layout (standard conversion)
    @classmethod
    def get_form_layout(cls) -> layout.L:
        return layout.L(sections=[
            layout.S(rows=[...]),  # plain style — side panel header provides title
        ])
```

#### Why Each Change is Needed

| Change | Why |
|--------|-----|
| `modal_template_name = 'common/form_side_panel.jinja'` | `ModalMixin.dispatch()` uses this for AJAX requests. Without it, defaults to `form_modal.jinja` which renders in a modal. |
| `detail_sidepanel_view = True` | `table_list.jinja` checks this to emit `data-toggle="side-panel"` on list item links. Without it, clicking an item name navigates to a full page. |
| Override `get_list_buttons()` | `GenericCRUDL.get_list_buttons()` hardcodes `open_in_modal=True`. Must override to use `open_in_sidepanel=True`. |
| `form_base_class = GenericEditTailwindForm` | Swaps the dynamic TmpForm's parent from Bootstrap to Tailwind so `form.is_tailwind_form = True`. |

#### Template Guard on `form_side_panel.jinja`

The shared `form_side_panel.jinja` currently renders `{{ form|bootstrap }}` only. If converting a form to Tailwind and using this shared template, you must add the `is_tailwind_form` guard:

```jinja
{% if form.is_tailwind_form %}
  {{ render_form(form) }}
{% else %}
  {{ form|bootstrap }}
{% endif %}
```

Plus the import: `{% from 'forms/form.jinja' import render_form %}`

This guard is needed because other CRUD classes may still use `form_side_panel.jinja` with Bootstrap forms.

#### Full Page vs AJAX — Both Templates Matter

GenericCRUD forms render in **two contexts**:
- **AJAX** (button click from list) → `modal_template_name` → side panel template
- **Direct navigation** (typing URL, or redirect) → `edit_template` → `common/edit_basic.jinja` (full page)

`edit_basic.jinja` already has the `is_tailwind_form` guard, so the full-page path works automatically after setting `form_base_class = GenericEditTailwindForm`.

## Converting Formsets (Template-Only)

Django formsets (`formset_factory`, `BaseFormSet`) repeat multiple copies of the same form in a loop. The standard `get_layout()` / `render_form()` pattern **does not apply** — the template controls layout, not the form class.

### Why Formsets Are Different

- `render_form()` wraps sections in `basic_card` — this would nest cards inside table rows
- Formsets iterate over forms in a `{% for form in formset %}` loop — there's no single form to call `render_form()` on
- The form class is often plain `forms.Form` (not `TCBSForm`), so there may be no Python changes needed at all

### What Changes

**Template only.** Replace `{{ form.field|bootstrap }}` with `{{ render_field(form.field) }}` inside the formset loop. No Python form class changes.

### What Does NOT Change

- **Form class** — no base class swap, no `get_layout()` method
- **Formset class** — `BaseFormSet` subclasses stay as-is
- **JS file** — formset plugins (e.g., jQuery formset) manage add/remove rows; leave untouched
- **Functional CSS classes** used by JS (see gotchas below)

### Conversion Steps

1. **Add template imports:**
   ```jinja
   {% from 'forms/form.jinja' import render_field %}
   {% from 'components/cards.jinja' import basic_card %}
   {% from 'components/button.jinja' import button %}
   {% from 'components/alert.jinja' import alert %}  {# if info/warning boxes exist #}
   ```

2. **Replace field rendering** inside the formset loop:
   ```jinja
   {# Before #}
   <td>{{ form.subject|bootstrap }}</td>

   {# After #}
   <td class="tw:py-3 tw:pr-4">{{ render_field(form.subject) }}</td>
   ```

3. **Handle raw widget fields** — some fields (e.g., `CheckboxSelectMultiple`) can't use `render_field()`. Render them with `|safe` and add errors manually:
   ```jinja
   <td class="tw:py-3 tw:pr-4">
     {{ form.qual_levels|safe }}
     {% for error in form.qual_levels.errors %}
       <p class="tw:text-sm tw:text-error tw:mt-1">{{ error }}</p>
     {% endfor %}
   </td>
   ```

4. **Wrap the formset table in `basic_card`** using the content capture pattern:
   ```jinja
   {% set content %}
     <table class="tw:w-full skills">
       <tbody>
       {% for form in my_formset %}
         <tr class="tw:border-b tw:border-border">
           <td class="tw:py-3 tw:pr-4">{{ render_field(form.field1) }}</td>
           <td class="tw:py-3 tw:pr-4">{{ render_field(form.field2) }}</td>
           <td></td>  {# empty cell for add/remove buttons injected by JS #}
         </tr>
       {% endfor %}
       {# empty form template for JS to clone #}
       {% with form = my_formset.empty_form %}
         <tr id="id_skills_empty_form" style="display:none;">
           <td class="tw:py-3 tw:pr-4">{{ render_field(form.field1) }}</td>
           <td class="tw:py-3 tw:pr-4">{{ render_field(form.field2) }}</td>
           <td></td>
         </tr>
       {% endwith %}
       </tbody>
     </table>
   {% endset %}
   {{ basic_card(card_header={'title': _('Section Title')}, content=content) }}
   ```

5. **Replace Bootstrap table classes** with Tailwind:
   - Table: `table table-striped table-hover` → `tw:w-full`
   - Header cells: add `tw:text-left tw:text-sm tw:font-medium tw:text-muted-dark tw:pb-3 tw:border-b tw:border-border`
   - Body rows: add `tw:border-b tw:border-border`
   - Body cells: add `tw:py-3 tw:pr-4`

6. **Replace static elements** with component macros:
   - Submit button: `{{ button(type='submit', variant='primary', text=_('Submit')) }}`
   - Alert boxes: `{{ alert(message, variant='info') }}`

7. **Remove `<style>` blocks** — replace inline CSS (e.g., column widths) with Tailwind utilities on `<th>`/`<td>` (e.g., `tw:w-2/5`).

### Formset Gotchas

#### JS class selectors are critical
Formset JS plugins use CSS class selectors to initialize. **Always grep the associated JS file before renaming or removing classes.** Example: a jQuery formset plugin using `$('.skills tbody tr').formset({...})` requires the `.skills` class on the table — removing it silently breaks add/remove buttons and form visibility.

#### Shared JS across multiple formsets
A single JS file may serve multiple formset pages (e.g., skills AND qualifications). Classes like `.skills` may be required on ALL formset tables, even if the table conceptually represents something else. Add both classes if needed: `<table class="tw:w-full skills quals">`.

#### Preserve these functional identifiers
These are JS dependencies, not styling — keep them intact:
- Table class used by formset plugin selector (e.g., `.skills`)
- Empty form row ID (e.g., `#id_skills_empty_form`)
- Form class (e.g., `form.main-form`)
- Formset container ID (e.g., `#skills_formset`)

#### Add/remove buttons are JS-injected
Formset plugins (e.g., jQuery formset) inject add/remove buttons at runtime with their own Bootstrap classes (`btn btn-success`, `btn btn-danger`). These buttons are NOT in the template — they can only be changed by modifying the JS.

#### Widget swapping doesn't apply
`TailwindForm.update_field_widgets()` swaps TextInput, URLWidget, FileInput to Tailwind versions. Select and SelectMultiple widgets are NOT swapped. Since formset forms typically use Select fields, no widget changes are needed — another reason why no Python changes are required.

## Planning: Dependency Analysis Before Starting

**CRITICAL**: Before converting any forms, map the inheritance hierarchy to avoid unexpected scope expansion.

### The Problem: Shared Base Classes

If you convert a shared base class, you implicitly convert ALL forms that inherit from it. This can cause:
- Tests failing in unrelated modules
- PR scope expanding from "convert CRM forms" to "convert all filter forms"
- Unexpected work in areas you didn't plan to touch

### Example: What Went Wrong with Filter Forms

```
Started: "Let's convert CRM forms"
    ↓
Discovered: CRM has ClientSearchForm (a filter form)
    ↓
Realized: Filter forms inherit from GenericFilterForm
    ↓
Problem: GenericFilterForm is used by 27+ forms across ALL modules
    ↓
Result: Had to convert ALL filter forms, not just CRM
```

### How to Avoid This

**Step 1: Identify what base classes your target forms use**
```bash
# Example: Check what CRM forms inherit from
grep -r "class.*Form.*:" TutorCruncher/crm/forms/ | head -20
```

**Step 2: Check if those base classes are shared across modules**
```bash
# If you see TCBSForm, check how many places use it
grep -r "class.*TCBSForm" --include="*.py" | wc -l

# If you see a specific base like GenericFilterForm
grep -r "GenericFilterForm" --include="*.py"
```

**Step 3: Choose your slicing strategy**

| Base Class Type | Strategy | Example |
|----------------|----------|---------|
| Shared across modules | Horizontal slice (convert ALL at once) | `GenericFilterForm` → convert all filter forms |
| Module-specific | Vertical slice (convert by feature) | `ClientEditForm` → just convert that form |
| Standalone (no inheritance) | Convert individually | Simple `TCBSForm` subclasses |

### Atomic Conversion Units (What MUST Be Converted Together)

These share base classes and must be converted as a unit:
- **All filter forms** - share `GenericFilterForm` (DONE)
- **All role filter forms** - share `GenericRoleFilterForm` (DONE)
- **All map filter forms** - share `MapFilterForm` (DONE)

These can likely be converted independently:
- **Individual TCBSForm subclasses** - most don't share custom base classes
- **Individual TCBSModelForm subclasses** - check for shared mixins first

### Quick Dependency Check Command

Before starting any conversion, run:
```bash
# Find all classes that inherit from your target's base class
grep -r "class.*YourBaseClass" --include="*.py" TutorCruncher/
```

If the count is high and spans multiple modules, plan for a horizontal slice.

Before starting conversion, verify:

## Common Gotchas and Edge Cases

### Variable Name Collision with `layout` Module
The Bootstrap pattern often uses `layout` as a variable name:
```python
# BAD - shadows the import after adding `from ...forms import layout`
layout = [{'title': '...', ...}]
return layout

# GOOD - rename to `sections`
sections = [layout.S(title='...', ...)]
return layout.L(sections=sections)
```

### Missing Titles in Original Layouts
Some Bootstrap layouts omit the `'title'` key. Whether to add a title depends on context:

**Modal forms** — do NOT add a title. The modal header already provides context:
```python
# Before (no title)
{'type': BSForm.TITLED, 'rows': [['field1']]}

# After (modal form — keep it plain, no title)
layout.S(rows=[['field1']])
```

**Full-page forms** — add a sensible title:
```python
# Before (no title)
{'type': BSForm.TITLED, 'rows': [['field1']]}

# After (full-page form — add title, card style is the default)
layout.S(title='Details', rows=[['field1']])
```

### Converting `show_extra_attr` Pattern
Bootstrap had magic handling for custom attribute fields that doesn't exist in Tailwind:
```python
# OLD Bootstrap pattern - DO NOT USE IN TAILWIND
{'title': 'Custom Fields', 'type': BSForm.TITLED, 'show_extra_attr': True, 'show_if': extra_attrs.exists()}

# NEW Tailwind pattern - USE THE HELPER FUNCTION
from TutorCruncher.common.forms.filter import get_custom_attr_layout_rows

if extra_attrs.exists():
    sections.append(layout.S(title='Custom Fields', rows=get_custom_attr_layout_rows(extra_attrs)))
```

### The `get_custom_attr_layout_rows()` Helper Function

**ALWAYS use this helper** when building layouts for custom attribute fields. It's defined in `TutorCruncher/common/forms/filter.py`:

```python
from TutorCruncher.common.forms.filter import get_custom_attr_layout_rows

# Usage - handles all attribute types correctly
if extra_attrs.exists():
    sections.append(layout.S(title='Custom Fields', rows=get_custom_attr_layout_rows(extra_attrs)))
```

The helper correctly handles:
- **Range types** (stars, integer, date, datetime) → `__from` and `__to` fields side by side (width 6 each)
- **Non-range types** (text, boolean, select) → single full-width field

### Why the Helper Exists: Ranged Attribute Fields

**CRITICAL**: Some attribute types create TWO form fields with `__from` and `__to` suffixes for range filtering. The ranged types are:
- `is_integer` (INTEGER type)
- `is_stars` (STARS type)
- `is_date` (DATE type)
- `is_datetime` (DATETIME type)

**DON'T manually build attribute rows** - use the helper instead:
```python
# WRONG - doesn't handle ranged types
attr_rows = [[a.form_field_name] for a in extra_attrs]

# WRONG - verbose and duplicates logic
attr_rows = []
for a in extra_attrs:
    if a.is_stars or a.is_integer or a.is_datetime or a.is_date:
        attr_rows.append([(f'{a.form_field_name}__from', 6), (f'{a.form_field_name}__to', 6)])
    else:
        attr_rows.append([a.form_field_name])

# CORRECT - use the helper
attr_rows = get_custom_attr_layout_rows(extra_attrs)
```

The field creation happens in `GenericFilterForm.add_attribute_fields()` which calls `AttributeDefinition.get_filter_field()`. This method returns a tuple of `(field_name, field)` for simple types, or `((name__from, field), (name__to, field))` for ranged types.

### Converting `show_if` Conditionals
Bootstrap used `'show_if': condition` inside the dict. In Tailwind, use Python `if`:
```python
# OLD Bootstrap pattern
{'title': 'Section', 'type': BSForm.TITLED, 'show_if': some_condition, 'rows': [...]}

# NEW Tailwind pattern
if some_condition:
    sections.append(layout.S(title='Section', rows=[...]))
```

### BSForm Import Removal - Check Entire File First
Before removing `from TutorCruncher.bootstrapform_jinja_plus.forms import BSForm`, search the file for:
- `BSForm.TITLED`
- `BSForm.CARD`
- `BSForm.UNTITLED`
- Any `Meta.layout` referencing BSForm
- Other forms inheriting from BSForm-related classes

Only remove when the file has zero remaining references.

### Different TITLED Sources
Watch for two patterns:
- `BSForm.TITLED` - requires the BSForm import
- `self.TITLED` - inherited from parent class (doesn't need BSForm import)

### Pre-built Section Objects from Mixins
Some mixins provide pre-built `layout.S()` objects that can be used directly:
```python
# self.map_filter_layout is already a layout.S() object from GenericAddressRadiusFormMixin
sections.append(self.map_filter_layout)
```

### Conditional Row Building
Don't forget to update conditional row appends:
```python
# Before (Bootstrap)
if condition:
    rows.append(['field'])

# After (Tailwind) - string format works since default width is 12
if condition:
    rows.append(['field'])  # This is fine! Default width is 12
```

### Width Inference from Original Layout
When the original has multiple fields in one row, divide 12 by the field count:
- 1 field → width 12 (can use string format: `['field']`)
- 2 fields → width 6 each (must use tuples: `[('f1', 6), ('f2', 6)]`)
- 3 fields → width 4 each (must use tuples: `[('f1', 4), ('f2', 4), ('f3', 4)]`)
- 4 fields → width 3 each (must use tuples)

### Regular Forms with Multiple Fields Per Row
**IMPORTANT**: The default width is 12, which means string format gives full-width fields. For forms that have multiple fields per row (common in edit forms), you MUST use explicit tuple widths:

```python
# This layout has 2 fields per row - MUST use tuples
rows=[
    [('first_name', 6), ('last_name', 6)],  # Two fields, 6 each
    [('photo', 4), ('user_email', 4), ('status', 4)],  # Three fields, 4 each
]

# This layout has 1 field per row - can use strings
rows=[
    ['description'],  # Full width
    ['notes'],  # Full width
]
```

### DateTimeField vs DateTimeInput (Field vs Widget)
When checking field types in form code, use **field classes** not **widget classes**:
```python
# WRONG - DateTimeInput is a WIDGET class, not a field class
if isinstance(self.fields[f], (forms.DateField, forms.TimeField, forms.DateTimeInput)):

# CORRECT - DateTimeField is the FIELD class
if isinstance(self.fields[f], (forms.DateField, forms.TimeField, forms.DateTimeField)):
```

This matters in `process_dt_format()` and similar methods that configure field widgets based on field type. Using the wrong class will cause date/time fields to not get their widgets configured properly, breaking date parsing in filters.

## Forms Without `get_layout()` Override

If a form inherits from an already-converted Tailwind parent (`GenericFilterForm`, `GenericRoleFilterForm`, `MapFilterForm`) and has no `get_layout()` override, it automatically uses Tailwind rendering. No conversion needed.

## Running Tests After Conversion

**ALWAYS use `uv run python ~/repos/run_test.py <test_name>` to run tests, NOT raw `pytest`.** The `run_test.py` script uses `--reuse-db` which skips migration creation and uses the existing test database. Running `pytest` directly tries to build the DB from scratch, which can fail due to migration ordering issues unrelated to your changes.

```bash

```

## Test Updates Required

When converting forms to Tailwind, tests may need updates:

### Context Variable Name Change
Tailwind filter forms use `search_form` instead of `form` in template context:
```python
# OLD Bootstrap - form in context as 'form'
assert r.context['form'].fields['field_name'].widget.attrs.get('data-url') == expected_url

# NEW Tailwind - form in context as 'search_form'
assert r.context['search_form'].fields['field_name'].widget.attrs.get('data-url') == expected_url
```

This change is in the view's `get_context_data()` method - Tailwind views pass the form as `search_form`.

### CSS Class Changes in Tests
Tailwind forms don't use Bootstrap CSS classes. Tests that check for Bootstrap-specific classes need updating:
```python
# OLD - Bootstrap forms had form-control class
assert 'class="select2-heavy  form-control"' in input_html

# NEW - Tailwind forms don't have form-control
assert 'class="select2-heavy "' in input_html
```

## Forms vs Modals — They Are Disjoint

**Forms and modals are separate concerns.** Understanding this prevents confusion during conversion:

- **Form** = Python class (fields, validation, `get_layout()`, `save()`). Lives in `forms/*.py`.
- **Modal** = UI container (popup box with header, body, footer buttons). Lives in templates like `form_modal.jinja`. Has JS for open/close/submit.

**When converting a form to Tailwind, you only change:**
1. The form class (Python) — base class, imports, `get_layout()`
2. The template rendering — `{{ form|bootstrap }}` → `{{ render_form(form) }}` (or `is_tailwind_form` guard)
3. The view button — `open_in_modal=True` or `open_in_sidepanel=True`

**You do NOT need to change:**
- Modal JS (open/close/submit logic)
- Modal template structure (header, footer, buttons)
- The modal's base template (`base-modal.jinja`)

The modal doesn't care what's inside it — it just renders whatever the form produces.

### `{{ form|bootstrap }}` Cannot Render Tailwind Forms

The `|bootstrap` filter only knows how to render Bootstrap forms. If you convert a form to `TCTailwindForm` but the template still uses `{{ form|bootstrap }}`, **fields will be missing** from the rendered output. This is why shared templates need the `is_tailwind_form` guard.

## Avoiding Card Nesting in Modals

`render_form()` wraps titled sections in a `basic_card` component (with a border and header). When a form renders inside a modal, this creates ugly visual nesting — the modal already has its own title/container.

**The fix**: Modal forms should use `plain` style by omitting the `title` on `layout.S()`. Without a title, the section defaults to `SectionStyle.plain` which renders fields directly — no card wrapper, no nesting.

```python
# WRONG — card inside modal = ugly nesting
layout.S(title='Client Details', rows=[['client'], ['name']])

# CORRECT — plain style, modal header provides context
layout.S(rows=[['client'], ['name']])
```

## Error Rendering Architecture

**IMPORTANT**: Understand where errors are rendered to avoid duplicates.

### Widget-Level Error Rendering
The Tailwind widget templates (e.g., `widgets/tailwind/input/_base.jinja`) render field errors:
```jinja
{% for error in widget.field_errors %}
  <p class="error-text">{{ error }}</p>
{% endfor %}
```

### Template-Level Error Rendering
The `render_field` macro in `forms/form.jinja` should NOT render errors because the widget already does it. If you see duplicate errors, check that `render_field` doesn't have:
```jinja
{# THIS WOULD CAUSE DUPLICATES - errors are already rendered by widget #}
{% for error in field.errors %}
  <p class="tw:text-sm tw:text-error tw:mt-1">{{ error }}</p>
{% endfor %}
```

### Non-Field Errors
Non-field errors (form-level validation) are rendered separately in `render_form`:
```jinja
{% if form.non_field_errors() %}
  {% for non_field_error in form.non_field_errors() %}
    {{ alert(non_field_error, variant='error') }}
  {% endfor %}
{% endif %}
```
